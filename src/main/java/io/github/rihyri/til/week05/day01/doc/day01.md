# Week 05 - Day 01. HTTP Session과 Session Clustering

<br>

## 1. HTTP와 Stateless

<br>

HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 데이터를 주고받기 위해 사용하는 프로토콜이다.

HTTP의 주요 특징 중 하나는 **Stateless(무상태)**이다.

- 서버는 각 요청을 독립적으로 처리한다.
- 이전 요청의 사용자 상태가 자동으로 유지되지 않는다.
- 서버의 확장과 요청 처리가 비교적 단순해진다.

하지만 로그인 상태나 장바구니처럼 여러 요청에 걸쳐 유지되어야 하는 데이터가 존재한다. 이러한 상태를 관리하기 위해 쿠키와 세션 등을 활용한다.

<br>

## 2. Cookie와 Session

### Cookie

쿠키는 서버가 브라우저에 전달하고, 브라우저가 저장하여 이후 요청에 포함할 수 있는 작은 데이터이다.

- 클라이언트 측에서 관리한다.
- 만료 시간 등을 설정할 수 있다.
- 인증 정보, 사용자 설정, 세션 식별자 등에 활용된다.
- 클라이언트에서 변조될 수 있으므로 중요한 정보를 그대로 신뢰해서는 안 된다.

<br>

### Session

세션은 여러 HTTP 요청 사이에서 서버가 사용자별 상태를 관리하기 위한 방법이다.

일반적인 서버 세션 방식에서는 실제 사용자 상태를 서버에 저장하고, 브라우저는 세션을 식별할 ID를 쿠키로 전달한다. 

#### 세션 인증 흐름

1. 사용자가 로그인 정보를 전송한다.
2. 서버가 사용자를 검증하고 세션을 생성한다.
3. 서버는 세션 ID를 브라우저에 전달한다.
4. 브라우저는 이후 요청에 세션 ID를 포함한다.
5. 서버는 세션 ID를 사용해 저장된 로그인 상태를 확인한다.

<br>

## 3. HttpSession

<br>

Spring MVC에서는 `HttpSession`을 통해 세션 데이터를 다룰 수 있다.

```java
// 세션에 데이터 저장
session.setAttribute("memberId", 1L);

// 세션에 저장된 데이터 조회
Long memberId = (Long) session.getAttribute("memberId");

// 특정 데이터 삭제
session.removeAttribute("memberId");

// 세션 무효화
session.invalidate();
```

- `setAttribute()` : 세션에 데이터 저장
- `getAttribute()` : 세션 데이터 조회
- `removeAttribute()` : 특정 데이터 삭제
- `invalidate()` : 세션 전체 무효화

로그인 상태처럼 사용자를 식별해야 하는 정보는 서버 측 세션에 저장할 수 있다.

## 4. 세션과 캐싱

<br>

세션은 로그인 정보 외에도 사용자별 데이터를 임시로 저장하는 데 사용할 수 있다.

이번 예제에서는 카테고리 조회 결과를 세션에 보관하였다.

#### 처리 흐름
1. 세션에 캐시 데이터가 있는지 확인한다.
2. 데이터가 있다면 DB 조회 없이 반환한다.
3. 데이터가 없다면 DB에서 조회한다.
4. 조회한 데이터를 세션에 저장한다.

단, 세션 캐시는 사용자마다 별도로 관리되므로 공통 데이터 캐싱에 적합하지 않을 수 있다. 캐시 갱신과 세션 메모리 사용량도 고려해야 한다.

## 5. 세션 관리 방식

<br>

서버를 여러 대 운영하면 세션 관리 방식도 중요해진다.

<br>

    <thead>
        <th>방식</th>
        <th>특징</th>
        <th>고려할 점</th>
    </thead>
    <tbody>
        <tr>
            <td>Local Session</td>
            <td>각 서버 메모리에 저장</td>
            <td>서버 간 세션 공유 어려움</td>

        <tr>

            <td>사용자를 특정 서버로 전달</td>
            <td>서버 장애 시 세션 유실 가능</td>
        </tr>
        <tr>
            <td>Session Replication</td>
            <td>서버 간 세션 데이터 복제</td>
            <td>네트워크 및 동기화 비용 발생</td>
        </tr>
        <tr>
            <td>Centralized Session Store</td>
            <td>Redis 등 공통 저장소 활용</td>
            <td>외부 저장소 관리 필요</td>
        </tr>
    </tbody>
</table>

<br>

**세션 클러스터링**은 여러 서버 환경에서 사용자의 세션 상태를 유지하고 공유하기 위한 기술 또는 구성 방식이다.

Sticky Session은 사용자를 항상 같은 서버로 보내는 방식이다. 구현이 간단하고 성능이 좋지만, 해당 서버가 죽으면 세션이 사라지고 부하가 한쪽으로 몰릴 수 있다.

세션 복제(Session Replication)는 각 서버가 세션을 다른 서버들과 복제해 공유하는 방식이다. 서버가 죽어도 다른 서버가 이어받을 수 있지만, 서버가 늘수록 통신 부하가 기하급수적으로 커질 수 있다.

마지막으로 중앙 집중 저장소 방식은 Redis나 Memcached 같은 외부 저장소에 세션을 두고 모든 서버가 조회하는 구조이다. 확장과 장애 대응이 유연해 요즘 표준으로 쓰이지만, 저장소 자체의 고가용성 구성이 필요하다.

## 6. 세션 기반 사용자 인증

<br>

세션을 이용한 로그인에서는 서버가 사용자를 인증한 뒤 세션에 사용자 식별 정보를 저장한다.

### 회원가입
- 입력된 회원 정보를 검증한다.
- 이메일 중복 여부를 확인한다.
- 비밀번호를 해싱하여 저장한다.

### 로그인
- 이메일을 기준으로 사용자를 조회한다.
- 입력된 비밀번호를 검증한다.
- 인증 성공 시 세션에 사용자 ID를 저장한다.

### 로그인 상태 확인
- 기존 세션이 존재하는지 확인한다.
- 세션에 사용자 ID가 저장되어 있는지 확인한다.
- 사용자 ID로 현재 회원 정보를 조회한다.

### 로그아웃 
- `session.invalidate()`를 사용하여 기존 세션을 무효화할 수 있다.

## 7. 실습 핵심 정리

<br>

- HTTP는 이전 요청의 상태를 자동으로 기억하지 않는다.
- 쿠키는 클라이언트가 데이터를 보관하고 전달하는 수단이다.
- 세션은 서버가 사용자별 상태를 관리하도록 돕는다.
- `HttpSession`으로 로그인 정보와 임시 데이터를 저장할 수 있다.
- 여러 서버에서 세션을 유지하려면 별도의 공유 전략이 필요하다.
