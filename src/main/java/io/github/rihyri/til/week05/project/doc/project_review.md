# Week 05 - Project : 회고

<br>

이번 과제는 이전에 학습한 Spring Security와 Redis를 활용하여 장바구니 기능을 구현하고, Redis 캐싱 전략을 적용하는 기능을 구현하는 것이었다.

기존에는 Redis를 주로 로그인 세션 저장소로 사용했지만, 이번에는 장바구니 조회 결과를 캐싱하는 용도로 활용해봤다.

Redis 캐싱 전략을 실제로 적용해보는 것은 처음이어서 어려움이 많았다.

특히 다음과 같은 내용들이 코드를 작성하며 어려움을 겪었다.

<br>

### 1. Cart와 CartItem의 차이

처음에는 사용자마다 장바구니가 하나씩 존재하므로 User와 Cart를 OneToOne 관계로 설계해야한다고 생각했다.

하지만 장바구니 자체를 관리하는 Cart 엔티티와 장바구니에 담긴 개별 상품을 의미하는 CartItem 엔티티 역할이 다르다는 것을 알게 되었다.

이번 요구 사항에서는 별도의 Cart 테이블 없이 userId와 productId를 이용해 장바구니 항목을 관리했다.

### 2. EntityGraph와 지연 로딩

CartItem에서 Product를 LAZY로 설정했지만, 장바구니 목록을 조회할 때는 상품 이름과 가격도 필요했다. 

처음에는 `@EntityGraph`가 생소했는데, 특정 조회에서 필요한 연관 데이터를 함께 로딩하도록 지정하는 기능이라는 것을 알게 되었다.

단순히 연관관계를 설정하는 것과 실제 조회 시 어떤 데이터를 함께 가져올지 결정하는 것은 별개의 문제라는 점을 배웠다.

### 3. Cache-Aside와 Write-Around

이전에는 Cache Hit과 Cache Miss의 개념만 알고 있었지만, 실제 API에 적용하면서 어떤 상황에 발생하는지 구체적으로 이해할 수 잇었다. 

특히 Write-around에서는 DB에 변경 사항을 저장하고 Redis에는 변경된 데이터를 바로 쓰지 않는다.

이때 기존 캐시를 삭제하지 않으면 이전 데이터가 반환될 수 있으므로 Cache Invalidation이 필요하다는 것을 알게 되었다.

### 4. RedisCacheManager와 TTL

이번에 가장 생소했던 부분 중 하나는 `CartCacheConfig`였다.

Redis 연결만 설정하면 캐싱이 자동으로 처리되는 줄 알았지만, Spring Cache를 사용하려면 캐시 기능을 활성화하고 CacheManager를 설정해야 한다는 것을 배웠다. 

### 5. ApplicationEventPublisher와 AFTER_COMMIT

처음에는 장바구니 데이터를 변경한 직후 Redis 캐시를 삭제하면 된다고 생각했다.

하지만 DB 트랜잭션이 아직 커밋되지 않은 상태에서 캐시를 삭제하면 다른 요청이 이전 DB 데이터를 다시 캐싱할 수 있다는 문제가 있었다.

이를 해결하기 위한 기본적인 방법으로 `ApplicationEventPublisher`와 `@TransactionalEventListener(AFTER_COMMIT)`을 학습했다.

DB 변경 이벤트를 발생하고, 커밋에 성공한 후 해당 사용자의 캐시를 삭제하도록 실행 시점을 구분할 수 잇었따.

다만 DB와 Redis가 하나의 트랜잭션으로 묶이는 것은 아니므로, Redis 장애나 동시 요청에 대한 추가적인 처리가 필요하다는 점도 알게 되었다.

<br>

이번 구현을 통해 Redis는 세션 저장소뿐 아니라 애플리케이션의 조회 성능을 개선하기 위해 캐시 저장소로도 활용할 수 있다는 점을 배웠다.

처음에는 새로운 어노테이션과 설정 클래스가 많아 이해하기 어려웠지만, 단순히 코드를 외우기보다는 요청이 어떤 순서로 실행되는지 파악하는 것이 중요하다고 느껴졌다.
