# Day 3. 회고

<br>

오늘은 Transaction, 영속성 컨텍스트, QueryDSL에 대해 학습했다.

트랜잭션은 여러 데이터베이스 작업을 하나의 작업 단위로 관리하여 데이터의 정합성을 보장한다. JPA의 영속성 컨텍스트는 엔티티를 관리하면서 1차 캐시, 쓰기 지연, 변경 감지 등의 기능을 제공한다. 

QueryDSL을 통해 문자열 기반의 JPQL 대신 Java 코드로 타입 안전한 동적 쿼리를 작성하는 방법도 배웠다.

### 1. Transaction과 Rollback

여러 쿼리를 실행할 때 하나라도 실패하면 전체 작업을 취소해야 한다는 점을 이해했다. 특히 주문과 재고 차감처럼 서로 연관된 작업은 하나의 트랜잭션으로 묶는 것이 중요하다.

### 2. Dirty Checking

영속 상태의 엔티티는 별도의 save() 없이 값을 수정하는 것만으로도 UPDATE가 가능하다.

JPA가 최초 스냅샷과 현재 엔티티를 비교하고, Flush 시점에 변경된 내용을 DB에 반영하기 때문이다.

### 3. Query DSL

검색 조건이 많아질수록 JPQL보다 QueryDSL이 편리하다는 점을 이해했다.

특히 BooleanExpressiond으로 WHERE 조건을 메서드로 분리하면 코드의 가독성과 재사용성이 높아진다.

수업을 들으면서 헷갈렸던 부분은 다시 정리하여 이해했다.

<br>

### 1. 1차 캐시와 동일성 보장

같은 ID로 조회한 두 엔티티가 왜 같은 객체인지 이해하기 어려웠다.

DB에서 조회할 때마다 새로운 객체를 만드는 것이 아니라, 이미 영속성 컨텍스트에서 관리 중인 엔티티가 있다면 해당 객체를 반환하기 때문이라는 것을 알게 되었다.

### 2. Flush와 Commit

처음에는 두 개념이 비슷하게 느껴졌다.

Flush는 변경된 내용을 DB에 전달하는 작업이고, Commit은 트랜잭션을 최종 확정하는 작업이라는 차이가 있다.

### 3. QueryDSL의 Q클래스

Q클래스가 어디서 생성되는지 궁금했다. Gradle의 Annotation Processor 설정을 통해 컴파일 과정에서 자동 생성된다는 것을 알게 되었다.

이번 수업은 지금까지 배운 JPA의 내부 동작을 이해하는 시간이었다.

특히 Dirty Checking과 Flush는 코드를 직접 실행하면서 SQL이 언제 발생하는지 확인해야 확실하게 이해할 수 있을 것 같다.

QueryDSL은 처음 접하는 문법이 많아 어렵지만, 기존에 작성하던 SQL과 비교하면서 공부하면 익숙해질 것 같다. 

앞으로 JPA 코드를 작성할 때 단순히 save()와 findById()를 사용하는 것에 그치지 않고, 영속성 컨텍스트와 트랜잭션이 어떻게 동작하는지도 함께 생각해야겠다.
